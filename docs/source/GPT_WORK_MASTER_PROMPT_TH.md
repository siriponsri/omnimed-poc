# 2) ทำความเข้าใจ Scope ต้นฉบับก่อนตัด POC

SRS เป็น **full HIS superset 53 modules** ไม่ใช่ backlog ที่ต้อง implement ทุกอย่างในรอบนี้

ก่อนเขียน code ให้:
- map module ที่เกี่ยวกับ OPD vertical slice
- extract requirement IDs ที่เกี่ยวข้อง
- แยก `IN_SCOPE`, `DEFERRED`, `OUT_OF_SCOPE`
- ระบุทุก assumption ที่ POC ลดทอนจาก production SRS

ต้องรักษา core concepts ต่อไปนี้อย่างน้อย:

- Party / Patient
- PatientIdentifier
- Encounter
- Observation / ObservationDefinition
- Order
- CatalogItem
- ChargeItem
- User / Role
- AuditEvent / PHI access audit
- Event Outbox concept
- FHIR R4 mapping boundary

### Core invariants ที่ห้ามละเมิดโดยไม่เปิด ADR

1. measured values เช่น BP, temperature, weight, lab result → `Observation` ไม่สร้าง ad-hoc columns ใน Encounter
2. Order ต้องผูกกับ Encounter
3. การแก้ Order ต้อง preserve history/revision ไม่แก้คำสั่งเดิมแบบสูญประวัติ
4. Clinical records ห้าม hard-delete ใน POC path ที่ implement
5. Finance role ต้องเห็น billing ที่จำเป็น แต่ไม่ควรอ่าน clinical content
6. Adapter boundary แยก external interoperability ออกจาก domain
7. POC ต้องยังเป็น **modular monolith** ไม่แตก microservices
8. product runtime ต้องทำงานได้โดยไม่ต้องมี LLM

# 7) Multi-Agent Control Plane

ใช้แนวคิดจาก `ai-agent-routing.zip`:
- Router วิเคราะห์ task
- Producer/Builder ทำงาน
- Checker ใช้ deterministic gates ก่อน
- Critic/Reviewer ตรวจเชิงคุณภาพ
- Controller ตัดสิน PASS / FIX / REROUTE
- จำกัดรอบ feedback

## Agents ที่อนุญาตใน starter นี้มีเพียง 4 บทบาท

### 7.1 Orchestrator
หน้าที่:
- อ่าน POC contract
- แตก milestone เป็น task contract
- เลือก route
- จำกัด scope
- ติดตาม dependency
- ตัดสิน escalation

ห้าม:
- เขียน product code เป็นค่าเริ่มต้น
- rewrite requirement โดยไม่มี evidence

### 7.2 Builder
หน้าที่:
- implement task
- เขียน migration
- เขียน tests
- update docs ที่เกี่ยวข้อง
- รายงาน changed files

### 7.3 SRS Guardian
หน้าที่:
- READ-ONLY reviewer
- ตรวจ implementation กับ SRS + POC contract
- ตอบ `PASS | FAIL | UNCERTAIN`
- อ้าง requirement IDs / contract clauses
- เปิด Finding เมื่อมี drift

ห้ามเขียน product code

### 7.4 Reviewer
หน้าที่:
- code quality
- security boundary
- maintainability
- test adequacy
- UX consistency
- dependency/license risk
- duplication / accidental complexity

## Execution route

```text
TASK CONTRACT
    ↓
BUILDER
    ↓
DETERMINISTIC GATES
(test / lint / typecheck / build / migration)
    ↓
SRS GUARDIAN
    ↓
REVIEWER
    ↓
PASS
or
FINDINGS → BUILDER
```

### Loop Budget
- normal task: max 2 repair loops
- hard blocker: max 3 loops
- หลังจากนั้น `BLOCKED_REQUIRES_HUMAN`
- ห้าม agent infinite retry

# 8) Model / Cost Routing สำหรับอนาคต

ตอน GPT Work สร้าง starter ให้เพียง **ออกแบบ interface/config** สำหรับ routing แต่ไม่ต้องเรียก paid API

สร้างตัวอย่าง config เช่น:

```yaml
routing:
  planner:
    class: high_reasoning
  builder:
    class: coding
  guardian:
    class: low_cost_reasoning
  reviewer:
    class: medium_reasoning
  escalation:
    class: high_reasoning
```

ห้าม hard-code model name ที่หมดอายุเร็วเป็น business logic

OpenRouter integration ในอนาคตต้อง:
- optional
- disabled by default
- read key จาก environment variable
- ไม่มี secret ใน repo
- มี mock/fake provider สำหรับ offline test
- model/provider routing อยู่ใน `.ai` หรือ tooling layer ไม่ปนกับ HIS domain

Reference:
- OpenRouter docs: https://openrouter.ai/docs
- OpenRouter examples: https://github.com/OpenRouterTeam/openrouter-examples
- OpenRouter skills: https://github.com/OpenRouterTeam/skills

# 11) Acceptance Scenarios — ต้องเขียนก่อน feature implementation

อย่างน้อยให้มี scenarios เช่น:

### A01 Registration
Given patient does not exist  
When R-REG registers synthetic patient  
Then Patient + HN + identifier are created  
And patient can be searched

### A02 Encounter
Given registered patient  
When OPD service begins  
Then one OPD Encounter is created and linked to patient

### A03 Triage
Given active encounter  
When R-SCR records BP/Temp/Weight  
Then values persist as Observations  
And no ad-hoc `encounter.weight_kg` style column is used

### A04 Lab Order
Given doctor opens encounter  
When CBC is ordered  
Then Lab worklist receives the order

### A05 Lab Result
When R-LAB validates Hb 10.2 g/dL  
Then result is stored as Observation  
And Doctor can view it

### A06 Medication
When Doctor orders Paracetamol 500 mg  
Then Pharmacy worklist sees the medication order

### A07 Dispense → Charge
When R-PHA dispenses medication  
Then a charge is generated from the clinical event

### A08 Finance Boundary
When R-FIN opens encounter billing  
Then charges are visible  
But SOAP/clinical result detail is not exposed

### A09 Audit
When protected patient data is read  
Then audit evidence exists identifying actor/time/context

### A10 FHIR
Given POC data  
When minimal FHIR endpoint/export is requested  
Then Patient/Encounter/Observation/ServiceRequest or MedicationRequest mappings are structurally valid for the supported subset

# 13) Security Rules สำหรับ POC

แม้ไม่ใช่ production ให้ตั้ง baseline:

- synthetic data only
- secrets via env only
- deny-by-default application RBAC
- Finance cannot view clinical content
- audit trail for implemented PHI reads
- password/auth mechanism สามารถเป็น POC-safe local auth แต่ต้องระบุว่าไม่ใช่ production IAM
- no real Thai citizen IDs in seed
- no hard-coded API key
- no clinical decision automation
- no claim that encryption/RLS is production-ready unless testedจริง

สร้าง `docs/SECURITY_BOUNDARY.md` แยก:
- implemented now
- scaffolded
- deferred production requirement
- known risks

### Plugin policy
- starter repo ต้องไม่ require plugin เพื่อ build/test/run
- plugin = developer productivity layer
- product domain = independent
- ทุก plugin ต้องมี reason-for-use
- ห้ามส่ง PHI ไป external plugin/model
- ใน POC ใช้ synthetic data เท่านั้น

# 18) README Standard

README ต้องดูเป็น professional healthcare open-source research/engineering POC

ต้องมี:
- What OmniMed POC is
- What it is NOT
- Scope diagram
- OPD demo journey
- Architecture diagram
- Quick start
- Test commands
- Demo accounts/roles
- Security disclaimer
- FHIR support matrix
- Project status
- Roadmap M0–M5
- Reference systems
- License/provenance note

ห้าม:
- “revolutionary”
- “game-changing”
- exaggerated AI claims
- fake compliance badge
- fake production readiness
- fake benchmark
- stock AI prose

# 20) M0 Implementation Boundary

GPT Work รอบนี้อนุญาต implement เพียงสิ่งที่จำเป็นเพื่อพิสูจน์ว่า starter runnable:

- backend health endpoint
- frontend shell
- DB connection
- migration smoke test
- minimal seed
- test infrastructure
- lint/typecheck/build
- Docker Compose

หากเลือกทำ feature เพิ่มเพื่อ prove architecture:
- ต้องเล็ก
- ต้อง tested
- ต้องระบุว่าเป็น spike
- ห้าม claim milestone complete

# 21) Validation Gate

ก่อนส่งมอบ ต้องรันสิ่งที่ทำได้จริงและบันทึกผลจริง

ตรวจอย่างน้อย:

- repository tree coherent
- no secrets
- no real PHI
- backend starts
- frontend starts/builds
- PostgreSQL starts
- migration runs
- tests pass
- lint passes
- typecheck passes
- frontend build passes
- Docker Compose config validates
- OpenRouter key not required
- no paid API required
- no hidden cloud dependency
- requirement trace exists
- POC scope frozen
- no out-of-scope modules accidentally implemented
- no fake feature claimed implemented
- README commands actually match repo
- Codex handoff is actionable

สร้าง:
- `validation/STARTER_AUDIT.md`
- `validation/FINAL_DELIVERY_REPORT.md`

ทุก claim ใน report ต้องมี evidence เช่น command + result

`omnimed-poc-starter-v0.1.zip`

# 23) STOP CONDITIONS

หยุดและเปิด Finding ถ้า:

- SRS contradiction ทำให้เลือก schema ไม่ได้อย่างปลอดภัย
- requirement ต้องพึ่งข้อมูล/มาตรฐานไทยที่ไม่ยืนยัน version
- มีแนวโน้มใช้ข้อมูลผู้ป่วยจริง
- ต้องใช้ paid API เพื่อให้ basic repo run
- architecture ต้องขยายเป็น microservices
- dependency license ไม่ชัด
- test ไม่ผ่านหลัง repair budget
- UI mockup กับ SRS ขัดกันใน semantic behavior

อย่าเดาแล้วเดินต่อเงียบ ๆ

# 24) Definition of Done สำหรับ GPT Work รอบนี้

ถือว่างานเสร็จเมื่อ:

1. starter repo เปิดได้และ structure professional
2. POC contract ถูก freeze
3. selected SRS requirements trace ได้
4. architecture/documentation consistent
5. M0 runnable/tested
6. Codex สามารถรับ TASK M1-01 ต่อได้ทันที
7. OpenRouter ถูกวางเป็น optional future provider
8. multi-agent control plane ถูกกำหนดแต่ไม่ over-engineer
9. ไม่มีการ claim full HIS / production / compliance
10. final audit ไม่มี unresolved Critical defect

หากไม่ครบ ให้ถือว่ายังไม่ส่งมอบ
